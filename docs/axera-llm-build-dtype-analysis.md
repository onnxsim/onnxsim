# How `pulsar2 llm_build` stores each weight dtype (AX650)

**Short answer:**

- `s8` and `s4` are per-row symmetric integer codes, packed as nibbles, with
  one float32 scale per output row.
- `fp16`, `bf16`, `fp8_e4m3` and `fp8_e5m2` all store **one float32 word per
  weight**, 4 bytes/param. The word holds the weight rounded to the requested
  type. All four float types compile to the same NPU program.
- The decode and prefill subgraphs share a single weight table. We found no
  duplicated copies.

Everything here was derived on a tiny 256-hidden model. Real checkpoints differ
in four places, listed under [On real models](#on-real-models).

`scripts/axera/llm_build_dtype_analysis.py` holds byte-exact encoders and
decoders for all six types. `tests/test_axera_llm_build_dtype_analysis.py`
checks them against ~136 KB of committed slices of our builds, with no Docker,
device or network.

## Method

This is black-box work on our own builds only. We did not consult or derive
from any third-party dump of vendor internals.

- **Checkpoint.** A one-layer synthetic Llama, generated by
  `tiny_llama_weights()`: hidden 256, 8 heads, 2 KV heads, intermediate 512,
  vocab 512, float32. `q_proj` is `RandomState(11)`; every other weight is
  `RandomState(3)`.
- **Builds.** One build per weight type, all with `pulsar2:7.0-lite`,
  `--prefill_len 64 --kv_cache_len 127 --parallel 1`. Each ran under a 24 GB
  memory cap, one at a time (`build_command()`). A build takes about 25 s.
- **Extra builds.**
  - An `intermediate_size=2048` variant, built as s8, s4 and bf16.
  - A second bf16 build and a second s8 build of the same checkpoint, to
    measure rebuild noise.
  - Marker checkpoints that give `q_proj` structured values:
    - `±(1+m/128)`, indexed by row or by column, for the float layout;
    - four `(c + f(r, c)) % 16` int4 patterns for the s4 layout.
- **Analysis.** In every per-layer `*_l0_together.axmodel` we compared the
  `npu_params` initializer with the encoders, block by block. Both subgraphs'
  MCode was decoded with `short_unit_codec.py`. It parses llm_build engines
  unchanged: 15 segments per subgraph, and every segment round-trips.

## Per-dtype table

Weight bytes/param are for the 256-hidden layer (557,056 Linear params). The
full `npu_params` figure adds the non-weight constants listed below.

| type | npu_params B/param | weight B/param | stored value | layout inside a 32-row block | scales / extra | MCode (decode subgraph records) |
| --- | --- | --- | --- | --- | --- | --- |
| `s8` | 1.194 | 1.164 | `q+128`, `q = floor(w/s+0.5)` clipped to [-128,127], `s = -w[argmax\|w\|]/128` | two nibble planes, 18 B apart, per 36-column chunk. 72-B unit = row `r` (36 B) + row `r+16` (36 B); pad columns hold the zero point | 512-B tail per 32 rows: 32×(int32 Q16.16 `-Σq/2`, 4 zero B), 128 zero B, 32 float32 scales | 9,843 |
| `s4` | 0.626 | 0.596 | `q+8`, same quantizer with `/8`, clipped to [-8,7] | one plane; byte = `(code[2j+1]<<4) \| code[2j]`. 36-B unit = row `2k` (18 B) + row `2k+1` (18 B) | 384-B tail: 32×int32 Q16.16 `-Σq/2`, 128 zero B, 32 float32 scales | 9,725 |
| `fp16` | 4.031 | 4.000 | float32 of `fp16(w)` (RNE) | column-major float32 words: column `c` = rows 0..31 | none | 6,408 |
| `bf16` | 4.031 | 4.000 | float32 of `bf16(w)` (RNE; low 16 bits are zero) | same as fp16 | none | 6,408 (same program) |
| `fp8_e4m3` | 4.031 | 4.000 | float32 of `e4m3(w)`, a plain cast with **no scale** | same as fp16 | none | 6,408 (same program) |

With `intermediate_size=2048` the figures are s8 1.167, s4 0.601 and bf16
4.010 B/param overall.

### Details that apply to more than one type

- **Scale.** There is one float32 scale per output row and no k-groups. It is
  positive when the row's largest-magnitude weight is negative. (The Qwen3-0.6B
  s4 build uses another rule, see [On real models](#on-real-models).)
- **s4 accuracy.** The s4 quantizer matches every code in both builds.
- **s8 accuracy.** The s8 quantizer misses 3 of 557,056 codes, and 10 of
  1,736,704 in the wide build. Every miss has `w/s` within 4e-6 of a .5 tie,
  and each time the compiler's code is one higher than ours. Its ratio
  arithmetic differs from float32 `w/s` in the last few ulps, and we have
  not identified how.
- **Column blocks (s8 and s4).** Each 32-row block is split by columns. The
  first column block holds up to 576 columns (16 chunks of 36) and every later
  one exactly 544, with as few 544-wide blocks as leave the first at most 576
  wide: `n = max(0, ceil((cin - 576) / 544))`, widths `cin - 544 n` then `n`
  times 544. So 2048 gives 416+544×3, and 4096 gives 288+544×7, matching the
  s8 split recorded in the README. The real models add 576 (one block), 1024
  (480+544), 1536 (448+544×2) and 3072 (352+544×5). An earlier version of
  this doc said "split once `cin > 544`"; that fits everything except 576,
  where it would give 32+544. Each column block is encoded like a whole matrix
  of its width, with its own tail. That tail repeats the full row's scale
  and carries the row sum over only its own columns. Float types are never
  split (bf16 at `cin=2048` is one block).
- **Deduplication.** A 32-row block that is byte-identical to an earlier one
  of the same Linear is stored only once. Marker checkpoints with identical
  rows shrank the table by exactly the repeated blocks, at s4 and at bf16.
- **Non-weight bytes.** These are the same in every type: 17,028 B on int
  types and 17,152 B on float types.
  - 128 float32 copies of `1/sqrt(head_dim)` at offset 0. Int types add a
    float32 `32767.0` after them.
  - A 127×32 float32 table with values in [-1, 1] that starts with 1.0s. It
    is consistent with a RoPE table for `kv_cache_len` 127. It sits
    *between* `k_proj`'s two blocks.
  - 256 B of `1/sqrt(head_dim)` at the end.
  - On float types, 128 zero bytes between `v_proj`'s two blocks.
- **Determinism.** `npu_params` is byte-identical across rebuilds.

### MCode differences

- **Float types share one program.** fp16, bf16, fp8_e4m3 and fp8_e5m2 give
  the same record count in every segment. The only record streams that
  differ are `a2/0000` in segment 0, `a8/0170` in segment 9 and `a8/0230` in
  segment 12. The same three streams also differ between two builds of the
  *same* bf16 checkpoint, so this is rebuild noise, not dtype. The float
  weight type therefore changes only how the stored float32 values are
  rounded, not the kernel.
- **s8 and s4 have their own programs.** Segments 0-5 hold 140-990 records
  each in the int builds, against 2 in the float builds (17 in segment 0).
  s8 against s4 differs in over 100 record streams.

## Verdicts on the external hypotheses

These are the hypotheses from `woolcoxm/Axera-AX8850-GGUF-Support`, tested
against our builds.

| # | hypothesis | verdict |
| --- | --- | --- |
| H1 | s8 layer engines store int4 nibble pairs: byte = `(hi<<4)\|lo`, +8 offset, hi = odd k | **Refuted for s8; it describes s4 exactly.** s8 stores int8 codes `q+128`, split into a low and a high nibble plane 18 bytes apart. Each plane byte does pair column `2j` (low) with `2j+1` (high). The high plane is `(q>>4)+8`, which is where the "+8" comes from. Reading one plane as int4 loses the other half of every code. An `s4` engine is exactly the described format: `code = q+8`, `byte = (code[2j+1]<<4)\|code[2j]`. |
| H2 | per-(row, 256-k-group) `[int16][bf16]` scale entries | **Refuted.** Each row has one float32 scale, stored in a per-32-row tail after 32 row-sum entries and 128 zero bytes. A 256-wide group never appears: `down_proj` at `cin=512` has a single scale per row. The s8 row-sum entry is 8 bytes: int32 Q16.16 `-Σq/2`, whose low half is `0x0000` or `0x8000`, then 4 zero bytes. That shape reads naturally as "[int16][something]". Only at `cin > 544` does a row carry several tails, one per 544-wide column block, and they repeat the *same* scale. |
| H3 | ~40% of the bytes are duplicated decode/prefill copies | **Not reproduced.** Both subgraphs name the same `npu_params` (`const_data_key`). Every weight block appears exactly once, and non-overlap is checked in the test. Everything outside the weights is 2.6% (s8), 4.9% (s4) or 0.8% (float) of the table. llm_build actively deduplicates identical blocks. |
| H4 | 36 unexplained metadata bytes per 72-byte unit | **Refuted.** In s8 a 72-byte unit is row `r`'s two planes followed by row `r+16`'s two planes, so the "metadata" half is another row's weights. The test decodes it as row 16. |

## On real models

Found later on the s4 builds of SmolLM2-135M (hidden 576) and Qwen3-0.6B
(hidden 1024), and used by `scripts/axera/llm_int4_requant.py`. Details and the
byte map of a whole layer file are in `docs/axera-llm-int4-requant.md`.

- **Quantizer.** SmolLM2's build uses the rule above. 3,535 of its
  106,168,320 s4 codes differ from `quantize_int`: each is an exact .5 tie
  that the compiler rounded down, and its tie rule is not identified.
  **Qwen3's build uses a different rule**: `s = max|w| / 7`, always positive,
  `q = rint(w / s)` (half to even), codes in [-7, 7]. That matches all
  440,401,920 codes, and every scale bit for bit. We do not know what selects
  the rule. `llm_int4_requant.quantize_plain` has both.
- **Column blocks.** `cin = 576` is a single block; `column_blocks()` was
  corrected (see above).
- **Row blocks.** SmolLM2's `q_proj`, `k_proj` and `v_proj` are stored in
  blocks of **64 rows**, not 32. A 72-byte unit holds chunk `c` of rows `2k`,
  `2k+1`, `2k+32`, `2k+33`; the tail is 64 row sums, 256 zero bytes, 64
  scales. Its other four Linears, and all seven on Qwen3, use 32 rows. The
  encoders in `llm_build_dtype_analysis.py` cover 32 rows only;
  `llm_int4_requant.py` covers both.
- **Post model.** It is s8 whatever `--weight_type` says: the `npu_params` of
  the s4 and s8 builds' post models are byte-identical, on both models.
  `lm_head` is stored in the s8 layout above. On Qwen3 its quantizer is
  `s = max|w| / 127`, `q = rint(w / s)`.
- **Embedding.** It is in no compiled file. The host looks it up from the
  checkpoint.

## Not covered

- Hidden sizes whose `cin mod 544` is between 1 and 31: the column-block rule
  has not been tested there.
- What selects the quantizer rule and the 64-row blocks.
- Activation dtypes other than `--hidden_state_type bf16`.
- Any on-device run. This task did no device work.
