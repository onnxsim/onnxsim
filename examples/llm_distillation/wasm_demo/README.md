# Knowledge distillation, live in the browser (WASM)

`index.html` runs real knowledge-distillation training entirely client-side, via ONNX Runtime
Web's on-device training API (`ort.TrainingSession`) -- unlike `scripts/pyodide_demo/` (which
runs onnxsim's own `simplify()`/quantization passes client-side), this one *trains* a model, live,
in a browser tab, no server-side compute involved.

## What's actually running

- A tiny student model (matching `examples/llm_distillation/distill.py`'s `TINY_SPEC` architecture
  -- `hidden_size=32`, 2 layers, real attention/RoPE/RMSNorm/SwiGLU, ~22K parameters) trains against
  a frozen teacher of the same architecture, via a real KD loss (temperature-scaled soft-target
  cross-entropy + hard-label cross-entropy, combined) and real AdamW optimizer steps.
- On a small, fixed pool of synthetic random-token examples (generated once, cycled through
  repeatedly) -- so the loss you see in the page actually converges, rather than bouncing around
  on an endless stream of unrelated i.i.d. batches.

**This is not the ~1B/~162M-parameter demo `distill.py` runs.** PyTorch has no WASM build at all,
and that scale is many times over WASM32's ~4GB linear memory ceiling regardless (see
`tools/onnx-finetune/wasm/README.md`'s sizing note) -- this page demonstrates the distillation
*mechanics* (real gradients, a real multi-input KD loss, real optimizer steps) working end to end
in a browser, at a scale that actually fits. It is also not a faithful next-token language-model
loss: the hard-label term is **position-aligned** (student's prediction at position *i* scored
against `labels[i]`, not a shifted next token) to avoid a dynamic `Slice` in the training graph --
see `generate_web_artifacts.py`'s `DistillationLoss` docstring.

## Regenerating the ONNX artifacts

`index.html` fetches four small files from `assets/` (checked into the repo, ~430KB total) rather
than exporting anything itself:

- `teacher_model.onnx` -- a plain inference-only export, run via `ort.InferenceSession`.
- `checkpoint`, `training_model.onnx`, `optimizer_model.onnx` -- the student's ONNX Runtime
  *training* artifacts (forward+loss graph, AdamW optimizer graph, initial parameters), produced by
  `onnxruntime.training.artifacts.generate_artifacts()` and run via `ort.TrainingSession`.

These were generated by `generate_web_artifacts.py`, which needs the heavy, non-onnxsim
dependencies this whole example already uses plus one more:

    pip install torch transformers onnxruntime-training

then:

    python examples/llm_distillation/wasm_demo/generate_web_artifacts.py

`onnxruntime-training` (not plain `onnxruntime`) is required specifically for
`onnxruntime.training.artifacts` -- the module that derives the backward/optimizer graphs. The
script also clamps every generated model's `ir_version` down to what the training runtime's
bundled C++ engine supports (10): the installed `onnx` package's own default (13 as of this
writing) is newer than that engine accepts, so without the clamp `ort.TrainingSession.create()`
fails with `Unsupported model IR version`.

## Serving it locally

Open via a static file server (not `file://`, since it fetches `./assets/*` over HTTP):

    python -m http.server 8000 --directory examples/llm_distillation/wasm_demo

then visit `http://localhost:8000/` and click "Start training".

## Validation notes

Confirmed working in real headless Chromium (via Playwright) as of this writing: the loss starts
around ~10.4 (near `ln(64)`, i.e. a freshly-initialized student's uniform-ish prediction over the
64-token toy vocabulary) and converges to a stable plateau within a few hundred steps as the
student fits the small fixed example pool -- genuine learning, not just steps that run without
crashing.

Two non-obvious things worth knowing if you touch this:

- **No cross-origin-isolation headers needed.** The `ort.training.wasm.min.js` bundle is a
  "threaded" WASM build, which normally needs `SharedArrayBuffer` (and therefore COOP/COEP response
  headers) for real multi-threading. Empirically, it falls back to single-threaded execution when
  `SharedArrayBuffer` isn't available rather than failing outright -- confirmed in headless Chromium
  with `crossOriginIsolated: false`. This isn't documented behavior to rely on if a future
  `onnxruntime-web` release changes it, just what was observed.
- **Pinned to onnxruntime-web 1.19.2.** That's the last release (of the versions available as of
  this writing) whose npm package still ships `dist/ort.training.wasm.min.js` / the
  `ort.TrainingSession` API at all -- later 1.2x releases dropped the dedicated training bundle
  from `dist/` entirely. Check before bumping the pinned CDN version in `index.html`.
